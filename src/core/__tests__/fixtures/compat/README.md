# Historical compatibility fixtures

These are synthetic, readable examples of historical serialization, not captures of user projects or files generated by 0.6.0. Each JSON contains the separate `autosave.project` / `autosave.runs` records, the portable `file` envelope, and independent expected prompts and image identities. Tests never execute historical code, launch the app, access a real folder, or contact a provider.

Sources inspected with local `git show`: `src/core/types.ts`, `src/core/compile.ts`, `src/core/models.ts`, `src/store/project.ts`, `src/store/persist.ts`, `src/store/runs.ts`; also `src/core/folders.ts` for 0.4/0.5. The v1 commit precedes all local release tags; the v0.1.0 tag is already schema v2. No tag was fetched. Later migration changes were read with `git log --oneline e5600c9..HEAD -- src/core/migrate.ts src/core/types.ts`.

Every example has three scenes (v1: four), a character with two pictures, a location picture, all five take statuses, a starred completed take with poster/video keys, and a transform scene with both frame assets. Presets are what every old project held: the three factory presets of `defaultPresets()` (identical in ae04bea and v0.1.0 – v0.5.0: `preset_draft` "Nháp", `preset_final` "Final", `preset_h3` "H3 nháp"; `preset_final` edited by the user — renamed in 0.2.0 / 0.4.2, settings changed in v1 / 0.3.0 / 0.5.0), then two user presets; scene 1 is linked to `preset_draft`. Image reference order differs between scenes to catch accidental asset sorting or collapsing a multi-picture character to one slot. PNG data URLs are tiny test payloads; media bytes, MIME type and remapped picture identities are checked during import. Video/poster keys are retained, but those video blobs are not embedded: historical exports did not include takes or videos.

`expected` holds per scene: `prompts` (after migrate), `imageKeys` (every numbered picture), `sentImageKeys` (what a request carries: the mode and model cap decide), `unsent` (red tokens, never sent) and `blocks` (the run rule that stops the scene, or null). `v1.json` adds `v1Sent` / `v1Generated`: the texts the ae04bea compiler produced for its scenes and the paragraphs it generated — computed once, offline, by running that historical compiler, and stored as data (the tests themselves never run historical code). v1's takes carry those texts as `promptSnapshot`, as v1 wrote them.

The 0.2 – 0.5 scene 2 also holds the other @video spellings old builds left in prompts: `@Video 2`, `@video3` (typed; tokens since 0.3) and `@video_?4` (written by `UNBOUND_RE` when a reference video went away). The 0.5.0 scene 1 glues a description to a token (`@image_1(cô gái)`), which 0.5 sent as text.

Expected changes are explicit:

- v1: enabled before/after blocks are folded into the prompt, their outer whitespace and the body are trimmed, paragraphs join with two LF characters, and a linked `@Tag` mention becomes what v1 compiled it to: the asset's first image slot when the scene sent reference images (Seedance 2.5 in every mode, MiniMax-H3 only in i2v) and that picture was within the model's cap (30 / 9); otherwise the asset NAME, as v1 sent it (an H3 transform / t2v scene, a picture past the cap). Unlinked mentions become the name too. Blocks, overrides and continuity links are removed. The generated "References (upload in this order…)" paragraph and "Continue directly from the previous scene…" line are not written into the prompt (SPEC-v2: both generators were removed): the migrated prompt is exactly the v1-sent text minus those paragraphs. Historical take snapshots, which include them, remain unchanged.
- v2: saved prompt strings stay byte-identical, including Vietnamese characters, leading/trailing spaces and CRLF. Compilation trims outer whitespace, as documented by the compiler; it must not mutate the stored prompt.
- 0.6.0: old video links/snapshots move to `legacyVideoRefs` / `legacyVideoRefsSnapshot`; active lists become empty. All `@video` text (`@video_1`, `@Video 2`, `@video3`, `@video_?4`, "Continue from @video_1:") stays intact, is marked invalid by the highlighter, and is blocked by run rules and gateway preflight.
- 0.6.0: a description glued to a token (`@image_1(cô gái)`, 0.5) is sent only when it names the picture the number stands for; here it does not, so the scene is blocked ('mismatch') until the user picks a fix (SPEC-v2). The text is kept byte for byte.
- Presets: kept exactly as saved, factory ones included (this branch has no preset rename). A factory-name migration (cx/arrange `renameFactoryPresets` + `Project.presetNames`) must update `compat.test.ts` / `compatPersist.test.ts` and this list: which presets are renamed (only untouched factory ones), the mark, and that both survive re-migration, export, import and reopen.
- Import: new project/folder/image IDs, fresh `updatedAt`, no takes, no archived video links, and no local folder paths. Old `videoLabels` do not rewrite prompts. These are intentional import semantics, not a claim of byte-identical import IDs.
- Export: folder path becomes null and links to takes are omitted. Local autosave retains both. Export/load/export and autosave/load are idempotent after normalization.
- Canvas spacing is separate from data migration: old 280 × 200 cards at 248px row intervals become rows suited to 352 × 304 cards. It is one undo step, including hand-placed takes and folder positions; reopening after undo does not repeat it. A spaced project under a new ID needs no second step.

Known issue (outside this suite's boundary, `components/canvas/rowSpacing.ts`): v1's grid puts cards 328px apart side by side, which the 352px node no longer fits (24px overlap); the one-time spacing only moves rows down, so a v1 row becomes a zig-zag. `compatPersist.test.ts` keeps this as `it.fails` until rowSpacing handles side-by-side cards.

Imported-job and foreign-model markers arrived after v0.5.0. Tests derive explicit post-release variants rather than putting these fields into the released fixtures. Bare old placeholders and later labelled placeholders are covered separately for the same reason.
