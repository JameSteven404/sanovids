# Spec v2 — current 0.6.0 behaviour

Historical feedback below explains the original direction; the sections describe the current implementation, including retired features. This is not release or visual acceptance.

User feedback (Vietnamese, paraphrased):
1. "When I create a video, a video node should come out of that scene node (connected), so I can continue scenes from that video into other nodes."
2. "Prompt blocks and the auto references paragraph are redundant. The prompt itself contains the references, numbered like @image_1."
3. "Improve features and optimize so it runs on the web or as an app."

## 1. Take nodes (video output on the canvas)
- Every take (generation attempt) is a **Take node** on the canvas (`type: 'take'`, `id = take.id`), connected from its scene with an edge `out:<sceneId>-><takeId>` (always drawn in a subtle style when visible by edge mode; highlighted with the scene).
- Default placement: a horizontal strip to the right of the scene, calculated by `defaultTakePosition` from the actual scene/take widths and row layout (oldest first). Positions are stored on the take (`take.position`, runs store, not undoable) once the user drags it; until then computed.
- Take node: full-frame poster/video (contain, letterboxed), title `S03 · T2` and rename field above the top-left; a 30 px playback bar below the picture, then settings and the large save/run-state button. Finished video has no overlay hiding the frame. Resize preserves the frame; "Phóng to" fullscreens the picture plus controls. The video element stays mounted in the same place when controls change.
- Take display (project-wide, `ui.takeDisplay`; canvas toolbar "Take: Tất cả / Chỉ take chọn", also in Settings): "Chỉ take chọn" shows per scene only the ★ take, else the newest completed one (else the newest), with a "+N" badge for the scene's hidden takes. There is no per-scene collapse.
- **Reference videos were retired in 0.6.0** ("bỏ video tham chiếu, giữ lại ảnh tham chiếu"; see §2.1). A take is never wired to a scene: its purple dot only goes into a "Thư mục" node (`save` wire); dropped on a scene card (or the prompt editor) it links nothing and shows "Video không dùng làm tham chiếu được nữa — kéo vào Thư mục để lưu". There is no `vref` edge any more (the kind is never reused with another meaning).
- Drop a finished take (or its wire) on empty canvas → "Tạo cảnh tiếp theo từ video này" (`actions.createSceneFromVideo`, ConnectMenu's first item): a new scene next to the take (right of it when it was dragged out of its row, else below the source scene) with the reference images and settings that take was made with (`take.refsSnapshot` minus deleted assets, `take.settings`; the source scene's preset only while it still matches), the source scene's frames and newer-build marker, and an EMPTY prompt — one undo step. A take of a model this build does not know, settings it cannot use as they are, or an imported take that is not sure of them → the source scene's current images and settings (the toast says so).
- Deleting a take (runs store) only drops it from folder nodes; prompts are never touched.

### 1.1 Playback keys
- Take viewer, node fullscreen and "Phát liền" share `src/core/transportKeys.ts`: Space play/pause; J/K/L reverse/stop/forward (repeat J/L: 1×, 2×, 4×); ←/→ one frame, Shift+←/→ five; Home start, End pause at the final frame rather than looping to zero.
- ↑/↓ changes take in the viewer, scene in "Phát liền", volume in the node's single-clip fullscreen. Backquote toggles fullscreen; Ctrl+backquote is also available on Windows. Escape leaves fullscreen first; a second Escape closes a viewer/dialog. F also exits node fullscreen.
- Text input/IME and focused native controls retain their own keys. Tab stays within fullscreen controls; canvas shortcuts never leak through the node's fullscreen player. These are code/tested rules; mouse, focus, resizing and playback still require manual GUI verification.

## 2. Prompt = exactly what the user writes, with @image_N
- REMOVE prompt blocks (data, store actions, sidebar panel, inspector toggles, import detection) and the auto "References…" paragraph and auto-continuity line. Remove scene `continueFrom` and the scene→scene "seq" edges/handles.
- Numbering: images numbered 1..N in `scene.refs` order (each image of an asset gets its own number, primary first).
- The compiled prompt = the scene prompt text unchanged. Legacy `@Tag` mentions (asset tags) are still converted to `@image_N` at compile time for robustness, but the editor inserts `@image_N` directly.
- **Auto-renumbering**: whenever refs change (remove, reorder, insert, asset images added/removed/reordered), rewrite `@image_N` tokens in the affected scene prompts so each token keeps pointing at the same image. The token of a removed image becomes a red placeholder `@image_?N(label)` (§2.2: no prompt text is ever lost), and the user gets a toast with Undo. All in the same undo step as the ref change. `@video` text is never rewritten (§2.1).
- Validation warnings: token number > available count ("@image_5 nhưng chỉ có 3 ảnh"), connected media never mentioned (info, still sent), over model limits, empty prompt, prompt length limit.
- PromptEditor: `@` popup lists (a) connected images with their numbers + thumbnails, (b) library assets not yet connected ("Nối & chèn" → connects and inserts the new number), filtered by typed text (matches name/tag/number). A token legend under the textarea: `@image_1 [thumb] Elara`; hovering a legend item highlights the token occurrences. Token highlighting inside the textarea via a backdrop mirror layer (colored `@image_N` teal, invalid red, retired `@video` text red and struck through).
- Scene cards show numbered image references; the node itself is the prompt editor (§2.3).

### 2.1 Retired reference videos (`@video_N`, 0.6.0)
- Old data stays loadable, schema 2. `migrateProject` moves a scene's old `videoRefs` to `legacyVideoRefs` (kept inert; `videoRefs` is always `[]`, also written so a 0.5.0 build reads "no reference video"), `migrateTake` moves `videoRefsSnapshot` to `legacyVideoRefsSnapshot`. Only the open-project notice reads them; they are never copied to a new / duplicated scene and are dropped on project duplicate / import (the takes do not travel). Exports no longer write `videoLabels` (old files' are ignored).
- The user's rule: the app NEVER removes or rewrites prompt text when a reference goes away. `@video_1`, `@Video 2`, `@video3`, `@video_?4`, `@video_?4(S01·T1)` and `Continue from @video_1:` stay byte for byte through migrate, renumbering, restore, duplicate and import. `video` stays in every token regex (so "@video1" never reads as a legacy @Tag and no asset can take the tag "video_1"; guarded by `src/__tests__/tokenRegexGuard.test.ts`).
- Such text is never sent and blocks the run until the user edits it. ONE helper finds it — `core/compile retiredVideoTokens` (the token parser's spellings + labelled placeholders) — for every layer: `compileScene` (`retiredTokens`, also in `unsentTokens`, one warning), `core/runRules` (rule 7 "Prompt còn @video_1 — SanoVids đã bỏ video tham chiếu: xoá hoặc viết lại chữ đó để chạy", before the image-only unsent-token rule), the gateway's `mapping.validateRequest` (canvasapp and development mode: refused before any upload / canvas save / job POST, after the adapter's ledger lookups, no credit), and the red marks (prompt editor, final preview, queue / take viewer, dev panel). `core/__tests__/retiredVideoParity.test.ts` checks they agree on every spelling. A scene that once used reference videos but whose prompt names none runs with its images.
- Quick fixes, only on a click, one undo step each (`src/videoRetired.ts`, store `setPrompts`): "Xoá @video_1" (every occurrence of that token, label included; a doubled space collapses), "Xoá câu “Continue from @video_1:”" (only when the prompt starts exactly with the starter older builds wrote) in the prompt editor, and "Xoá chữ @video ở N cảnh đang chọn" in the multi-scene inspector.
- Open-project notice, once per project on this device (`bdp:hint:video-retired:<projectId>`, `initRetiredVideoNotice` in main.tsx watches the project id): how many scenes still hold @video text and how many only had links, with "Xem" (select + reveal them).
- Takes of a deleted scene are no longer kept on the canvas (they stay in the queue drawer).

### 2.2 Red placeholders when a reference image is removed (GT1, 0.6.0)
- The user's rule: cutting a reference image from a scene NEVER deletes prompt text. On every removal path — wire cut / × / wire end dropped on the canvas (`edges.cutEdge` → `removeRef`), Delete on wires (`deleteItems`), × in the inspector, "Bỏ khỏi cảnh" (asset panels, multi-scene `removeRefs`), moving a wire end to another scene (`moveRefToScene`, source scene), removing one picture of a character (`updateAsset`), deleting a character from the library (`removeAssets`), restoring a take, and the undo / redo of all of these — the token becomes `@image_?N(label)` (store `withMedia`, `remapTokens` option `placeholder`): N = the old number, label (`core/placeholders removalLabels`) = the character's name ("Tên" for picture 1 of a removed character, "Tên · ảnh k" for later pictures and for every picture removed while the character stays linked), its unique tag when another character has the same name or the name is blank, sanitized (`core/tokenLabels sanitizeLabel`: NFC, no `( ) [ ] @ ?` / line breaks, ≤ 40 code points + "…"), bare `@image_?N` when the character is unknown. A "(…)" already glued to the token is kept byte for byte: it stays the label when it fits the removed picture (`@image_2(Lumi)` cut from Lumi → `@image_?2(Lumi)`), otherwise the new label goes in front of it and it stays plain text (`@image_2(cười)` → `@image_?2(Lumi)(cười)`). The other tokens renumber as before; with "Tự đánh lại số" off they keep their numbers as written and only the removed picture's token turns red (stale numbers are still reported).
- Restore from a take: a character that still exists but lost a picture → labelled; a deleted character → bare; an older take without `imageKeysSnapshot` → every `@image` from the first deleted character on becomes a bare placeholder (never a guess; `uncertain`).
- Placeholders block every run path: `compileScene` (verbatim in `unsentTokens`, warning), `core/runRules` (rule 8: "Còn chữ đỏ chờ ảnh: Lumi (@image_?2) …" before the generic sentence), the gateway's `validateRequest`. A real token with a glued label (`@image_2(Lumi)`: the "?" deleted by hand) is sent only when the label fits the picture its number names now (`labelFitsSlot`: name — or tag when shared — and " · ảnh k"); otherwise it blocks ("@image_2 đang là “Làng”, không phải “Lumi” …") — this also blocks a 0.5 prompt that glued a description to a token (`@image_1(cô gái)`) until the user picks "Giữ @image_1, giữ chữ" (one space added, nothing deleted) or another fix. Older builds since 0.2.0 also block a placeholder (their `UNBOUND_RE` reads its start). No schema change, no migration.
- Filling is always explicit, one undo step each, a refused fill changes nothing (store `fillPlaceholder` / `fillPlaceholders` / `fillPictureSlot` / `replaceRef`, plans `planFill` / `planReplace`): the shared "Chữ đỏ chờ ảnh" bar on the scene node and under the panel's prompt editor (`components/inspector/PlaceholderBar`: per group "Gắn ảnh đã nối", "Đổi thành chữ “Lumi”", "Xoá chữ đỏ"; for a label that does not fit "Giữ @image_2 = Làng, giữ chữ “(Lumi)”" (`splitTokenLabel`: a space before the "(", listed first) or "…, xoá chữ “(Lumi)”" (`keepTokenOnly`); "Đổi tất cả thành chữ"), the link toast "Gắn vào chỗ Lumi (N cảnh)" (`linkFillOffer`, only one new character and one label), and "Gắn ảnh mới vào chỗ ảnh k" after adding one picture to a character. Nothing is ever filled by itself (not even by the same name). With "Tự đánh lại số" off the character is appended; when a real token outside the group already uses one of the numbers it would take (left over by the cut, pointing at nothing), the fill is refused (`number-taken`, the token named) until that number is fixed — it would otherwise start sending the new character.
- Deleting a character that prompts name asks first (`assetDeleteImpact` / `assetDeleteQuestion`: "N cảnh … sẽ giữ chữ đỏ …"); unused ones delete without it. Toasts of every removal share `core/staleTokens mediaChangeNote`.
- Every highlighter reads the same segmentation (`inspector/tokens segmentPrompt` / `segmentForScene` + `labelChecker`): a placeholder with its label is one red segment; `findMention` never opens the "@" popup inside one. The stress tester checks X3 (image tokens keep their count) by default (`tokenKeep`).

### 2.3 Scene node is the editor
- Default "Bấm vào prompt": click the displayed text and type at that caret; Enter on the sole selected scene opens its prompt at the end. Settings expand in place; images and the costed "Tạo video" button stay on the card. Selecting a different scene closes the previous live node editor.
- Resting nodes render static text with the same wrapping/highlights as the live field; only one near node mounts the textarea. Below zoom 0.55, show code/name, a two-line prompt, images and Run; entering edit reveals the near node. "Tự mở khi chọn 1 cảnh" mounts without stealing focus; "Tắt" leaves editing in the right panel.
- "Khung soạn rộng" opens the panel composer. Opening it commits and closes that scene's node editor; returning to the node commits the panel. Drafts commit every 160 ms, on blur/unmount and lifecycle flushes. Escape first dismisses a mention popup, then commits/leaves the field without deselecting the node. Enter in the field inserts a newline; Ctrl/⌘+Enter commits then requests Run.
- Static/live node text and the panel share token highlighting and the "Chữ đỏ chờ ảnh" bar. Dropping one image on a placeholder (its chip, or right on the red text in the node's static text, live field or the panel's prompt) explicitly fills that group (or refuses with a reason). Dropping on prompt text links/inserts a token at the drop caret, moved past any word / token / red placeholder it would split (`snapToWordEnd`: the red text is never cut, so the scene stays blocked); several cards dropped on red text are inserted after it. Elsewhere a drop links the image and places a missing image tile. Link + insert changes only the prompt and references (one undo step; settings and a newer build's markers stay). File drops create image tiles and links in one undo step. No automatic fill merely because a name matches.

## 3. Desktop renderer and optimization
- SanoVids is distributed as a desktop app. The React renderer also runs locally for development/performance tests; PWA helpers remain in `src/lib/pwa.ts` and `vite.config.ts`, but this is not a promise of a supported public web deployment. The real gateway needs Electron; development access on other web hosts is locked.
- IndexedDB stores projects/runs/media, with localStorage emergency backup and v1 migration. Autosave is debounced; prompt drafts and storage flush on lifecycle changes. No `beforeunload` handler in the desktop app (it would cancel `quitAndInstall`); only the web renderer's "Nhập prompt" dialog guards unsaved pasted prompts / files with one.
- `src/App.tsx` renders Canvas only. `core/shownViews.ts` filters old view preferences to Canvas; there is no visible view switch. SceneTable is deleted. Storyboard remains hidden/frozen, not imported or bundled; its reorder UI is not a user feature.
- Memoized nodes, visible-node rendering, cached scene/asset lookups and near/far detail keep typing from scanning the entire project each key. Below zoom 0.55 the scene has two prompt lines and no live field. Large-project mode defaults to auto: from 800 cards, hide the minimap for the session and limit all-wires rendering near the viewport without rewriting the minimap preference.
- Dialogs and development tools load lazily. Headless tests and timing measurements do not establish visual smoothness on a user's machine.

## 4. Resizable side panels (done in the app shell)
- `components/common/PanelResizer.tsx`: drag the border between a side panel and the center to resize (left 200–520px, right 300–680px, center ≥ 360px), double-click resets, arrow keys ±16px (Shift ±64), dragging ~90px past the minimum collapses the panel. Widths persist in localStorage (`bdp:pref:leftW` / `bdp:pref:rightW`) and live in the CSS variables `--left-w` / `--right-w` on `.app`. Components must not hardcode panel widths.

## 5. Desktop app — Electron
- `electron/main.cjs` serves the built renderer through `app://bdp/`, preserving IndexedDB/localStorage origin across launches. Preload exposes narrow `app`, `files`, `canvasapp`, `devAccess` and `updates` bridges with context isolation and sandboxing; no renderer Node access. Packaged releases keep DevTools/debug switches off even after development-mode unlock.
- Product/app identity: SanoVids, `com.sanovids.app`, Windows Setup and Portable; project files `.sanovids.json` (old `.bdp.json` accepted). Agent tests never use the real `%APPDATA%\SanoVids`: Electron / packaged runs only with a test profile (`SANOVIDS_PROFILE_DIR` or a test build's baked `sanovidsTestProfileDir`), and test installers have their own appId / productName / executableName.
- Windows installer auto-updates only after pinned signature, product/version and file-hash checks; Portable checks then opens the release page. Signing, trust and publishing are owner operations (docs/SIGNING.md, docs/UPDATES.md). A development unlock does not weaken those rules.

### 5.1 Experimental Mac behaviour and release tooling
- Apple Silicon arm64, macOS 13+, DMG + ZIP; ad-hoc signed, not notarized. Install into Applications; other locations show placement guidance and default keep-login off. Mac updates are manual (`mac-manual`): check for a release, then open its page; no in-app download/install. A latest release without Mac files shows that fact (`noMacBuild`), never claims this is the newest Mac build and never hides a previously known update.
- Red close / ⌘W hides the window, keeping jobs running; Dock activation restores it. ⌘Q quits. A hidden window mutes audio immediately; only queued/running work keeps background processing and prevents idle sleep, after a 1 s settle. It releases that hold when work ends, on show or quit. This does not promise work during forced sleep.
- Native application/edit/window menus support Mac shortcuts; text right-click menus on Windows and Mac use native cut/copy/paste/select-all roles. Checkout is a normal child window on Mac so it can be closed. Mac folder-permission failures explain System Settings permissions; file names also respect Mac UTF-8/decomposed-length limits, leaving Windows naming unchanged.
- `npm run dist:mac` builds/inspects on Mac. `.github/workflows/mac-build.yml` never publishes: trial mac-ci/** pushes or manual builds, with a release candidate explicitly requested on main. Its test step currently allows failure; a successful workflow alone is not test acceptance. `scripts/mac-inspect.mjs` checks signing, entitlements, ASAR/fuses, licenses and identical app trees in DMG/ZIP; five artifact files last 3 days.
- Owner `npm run mac:fetch -- --run <number> [--attempt <n>]` fetches the specific tested RC (and attempt, when re-run), checks commit/run/SHA-512 and writes mac-fetch.json. Release group (k) requires those bytes and records before publishing. Local code/configuration checks do not verify a downloaded Mac app or a live CI run.

## 6. Saving video
- Completed takes have the large "Tải video" button on the node and in the take viewer. It saves the video plus a prompt .txt unless "Kèm file .txt chứa prompt" is off (`withPrompt`, default on); default base name `S03_T2 - <scene title>`, overridable by "Tên file" or the device naming template. Queue/processing/download states show progress; retries preserve the uncertain-payment rules in §12.
- Export chosen takes as a ZIP in scene order (★ else newest completed), with prompt export controlled by settings. This is available from current commands; the hidden Storyboard is not an entry point.
- "Hỏi nơi lưu & tên file" uses the desktop save dialog; automatic downloads use the chosen default folder. Canvas "Thư mục" nodes support explicit take saves and automatic completed-scene saves. Files never silently overwrite; writes use a temporary part file. Unavailable folders retain waiting saves until access is restored. Export/import of a project does not transfer local folder paths.

## 9. Development, legacy demo and real credits
- `src/lib/credits.ts` distinguishes 'dev' (simulated gateway balance), 'canvasapp' (the user's real account) and 'demo' (saved legacy mock takes only). `useCreditInfo` follows the effective gateway; balances reset when it changes. Unknown real balance displays "—", never an invented amount.
- DEV uses neutral/dashed labels, "credit dev" and a simulation hint. Real canvasapp credits come from `/api/me`; login, refresh and top-up all follow that gateway. Legacy "Demo cũ" cost lines keep their old local balance, with no new mock provider choice: the local demo wallet (store/runs `credits` / `spent`) starts at 1000 (`DEMO_CREDITS_DEFAULT`) for new runs data, keeps saved balances, and only saved mock takes were charged to or refunded from it (`resetDemoCredits` / `addCredits` remain store actions without a Settings control); dev and canvasapp takes never touch or wait for it. The credit pill shows a demo balance as play money and never invents a real one ("—" until known).
- `formatCredits`, `CREDIT_MARK` and take provider/charge metadata keep cost wording consistent in nodes, run confirmation, queue and viewer. Simulated top-up is a SePay simulation (§11), never a real payment. When development access is locked, its controls disappear (§11.1).

## 10. In-app top-up of canvasapp credits (2026-10-02)
User: "thêm khả năng nạp credit, thanh toán trong app" → chose: top up the user's OWN canvasapp account (not a SanoVids credit system).
Observed canvasapp flow (public client code, see docs/canvasapp-api-notes.md): `GET /api/auth/state` → `topup_enabled`; amount = integer VND, 10.000 ≤ amount ≤ 10.000.000, multiple of 1.000, credits = amount / 1.000, presets 30k/50k/100k; `POST /api/payments/topups { amount_vnd }` → `{ checkout_url, fields }` and the page auto-submits a hidden HTML form (POST) to `checkout_url` (SePay). SePay sends the browser back to canvasapp with `?payment=success|cancel|error&topup_order=<id>`; then poll `GET /api/payments/topups/{orderId}` → `status: pending|paid|reconciled|reconcile_required|expired|rejected` (order valid ~10 min; the site polls every 2 s for up to 2 min). History: `GET /api/credits/history?kind=all|topup|video|refund|adjustment&offset=0&limit=20` → `{ balance, items:[{type, description, status, delta, amount_vnd, created_at}], next_offset }`.
Design:
- Desktop only, through the canvasapp gateway session (`persist:canvasapp`). The bridge allowlist gains `POST /api/payments/topups`, `GET /api/payments/topups/:id`, `GET /api/credits/history`.
- New IPC `canvasapp:checkout({ checkoutUrl, fields })`: validates the URL (https only; host must end with `sepay.vn` — VERIFY on first real use, otherwise refuse with a clear message), opens a checkout window in the canvasapp partition (modal on Windows, a normal child window on Mac, §5.1) with a local page that POSTs the form, lets the user pay on the real SePay page (QR), and resolves `{ result: 'success'|'cancel'|'error'|'closed', orderId }` when the window navigates back to canvasapp.io.vn with `payment=…&topup_order=…` (or the user closes it). External links stay inside; no script injection into SePay.
- SanoVids never sees or types bank/card data; it never auto-confirms payments.
- UI: "Nạp credit" dialog (from the real-credit pill and the gateway settings section): presets 30k/50k/100k/200k + custom amount with validation and live "= N credit"; button "Mở thanh toán QR"; status view (Đang chờ thanh toán… with 10-minute countdown → Đã nhận tiền ✓ → refresh real credits; hết hạn / bị từ chối / đã huỷ / đang đối soát messages); "Lịch sử credit" tab with filters (Tất cả / Nạp / Tạo video / Hoàn / Điều chỉnh) and "Xem thêm". Disabled with explanations when not desktop, not logged in, or `topup_enabled` is false. Unlocked development mode has its own simulated account, credit history and SePay sheet (§11); no real payment.
- Tests: pure amount validation + status mapping + checkout URL validation; adapter/bridge with fakes. Never call the live API in tests.

## 11. Development mode replaces the demo (2026-10-02)
User: "đưa chế độ demo về thành chế độ phát triển dùng để tìm bug và sửa lỗi … có luôn các tính năng y như chế độ thật". The demo becomes a **development mode** that runs EVERY path of the real canvasapp mode, with no network at all.
- Providers: when development access is open, the saved choice selects 'dev' (initial choice) or 'canvasapp' with a desktop bridge. When locked, the effective provider is always 'canvasapp', but no new request is allowed until the user explicitly enables that gateway in Settings. A saved 'dev' choice then means real gateway off. Lock/unlock never overwrites that saved choice. Legacy 'mock' only serves previously saved takes. See §11.1.

### 11.1 Owner-controlled development access
- Release builds start locked. DEV credit controls, provider choice, panel links and stress tools remain hidden; the real gateway still requires explicit opt-in. Source/test builds are open by build type; a remote web host cannot unlock. Renderer state is only a strict mirror of the desktop decision.
- In Settings → Giới thiệu, five taps on the version within 3 seconds open the unlock box. It accepts a one-use, device-bound SV1 code signed by an owner's pinned Ed25519 key, or a 6-digit code from this device's linked authenticator. After an eligible SV1 unlock there is a 5-minute window to link that authenticator.
- "Giữ mở khoá": 1, 7 (default), 30 days or until manually locked, always capped by the code. Clock rollback/expiry/key removal can relock; wrong/replayed authenticator codes are refused and repeated wrong attempts wait. If the unlock state cannot be saved, access is session-only. Taking access away fails closed: a lock, shorter keep, expiry or authenticator removal that cannot be written (after retries) deletes the stored unlock state, so the next start is a new device and never opens again by itself. Email/Gmail unlock is not implemented.
- Relocking closes the dev panel and simulated login/payment/import surfaces. Already-running DEV jobs finish and saved videos stay viewable; new DEV submissions and retries stop. It does not switch an old simulated order into a real payment or grant debugging access.
- Owner tooling is `scripts/owner/mo-khoa.mjs` (never packaged); release checks require real public pins in `sanovids.devUnlockKeys`, reject missing/test keys and check the packaged identity. Documentation/tests do not provision owner keys.

- Only available with development access open and the simulated provider selected. ## 12. Gateway safety, login, downloads and site-job import
- **Keep-login**: a confirmed canvasapp login may be restored from an encrypted copy of that site's own session cookies, up to 30 days from login/cookie renewal. Ordinary use never extends the deadline. Default on for Windows installer/source and Mac Applications, off for Portable/other Mac locations; an unset default off (Portable shares `%APPDATA%\SanoVids` with Setup) neither restores, saves nor deletes the installed app's copy — only an explicit off, logout, expiry, a damaged file or a refusal of a copy that run restored/wrote deletes it. No Google/SePay/Cloudflare cookies are included; Google account cookies left by sign-in are separately cleared after confirmation. Server rejection clears the saved login; logout clears it first and blocks/aborts both requests and downloads. Failure to save/delete is reported, never described as successful persistence.
- **Bridge safety**: scene nodes are scoped to the SanoVids project, with legacy ids retained for running jobs/retries. A bridge rediscovered by name must be read back before saving it, keeping existing/running nodes. A confirmed account change resets bridge state; a submit begun under the old session cannot continue posting.
- **Unknown submit / double-charge protection**: before any job POST, save and read back its ledger record; no record means no POST. Lost replies trigger lookup, not a new take. The same body/key may be automatically resent once, only when the last readable of two fresh looks, 15 s apart, finds no candidate and proves (`listCovers`) that the job list reaches back to the original request; a look that cannot be read tells nothing. A job that might be it but cannot be attributed for sure (another unanswered submit on that node might own it, several could be it, or it cannot be told apart) stops it as "không rõ", never a resend. Missing entries in a truncated list prove nothing. Known/imported jobs are never reposted; multiple exact key matches follow one known job.
- If earlier evidence is missing/trimmed, belongs to another bridge or cannot prove absence, retry stops as "không rõ" / unverifiable. "Tạo lại" creates a new potentially charged take only on the user's command. Jobs on the same scene with competing unanswered submits cannot be claimed by each other or imported. The live site's idempotency support is still unverified.
- **Downloads**: finished video is paid before its local download completes. The app streams bounded chunks with progress, cancellation and HTTPS-only redirects. Resume requires a strong matching validator and server Range support; otherwise at most one restart from zero. Main-process caps are 1 GB, 4 MiB chunks, 60 s idle and 60 min per connection; a truncated response never becomes a completed take. Cancelling/deleting a paid pending download asks first. Dev uses smaller limits and simulated cut/stall/trickle/redirect/oversize faults (§11).
- **Nhập job**: read-only import from the gateway's bridge-session jobs, at most 20 per batch, pinned to the open project/provider. It claims eligible jobs as takes without creating jobs or charging again; completed remote jobs still pass through polling/download. Known, inferred (≈) and unknown (?) settings stay distinguished, and older node hints never overwrite newer job facts. Jobs that may belong to an unanswered SanoVids submit are excluded and checked again when claimed. A corrupt saved import marker stays unknown rather than becoming an ordinary take. "Chạy lại" means a new take, not reposting the imported job.

## 13. Library selection and deletion
- Library selection is independent of canvas selection. Click selects one card (a repeated click keeps it selected); Ctrl/⌘+click toggles, Shift+click adds the visible range, Ctrl/⌘+A selects the filtered visible cards. Escape, empty library space or the footer × clears it.
- Delete and the footer trash button act on selected visible cards only; hidden selections remain. "Xoá khỏi thư viện" in an item dialog targets that item through the same deletion flow. Unused images delete immediately. If deletion leaves red prompt placeholders or removes needed first/last frames, the app asks once before deleting. Drafts commit first; images, links and prompt remapping undo together. Media blobs stay for queued takes, shared projects and undo.
- No new selection is made after deletion; keyboard focus advances. The last area used decides whether Delete belongs to library or canvas; dropping a card outside or using a canvas command returns routing to canvas. A collapsed/empty library shows a hint instead of accidentally deleting canvas content. Windows Backspace never deletes (Vietnamese input tools use it); Mac ⌫ has a 90 ms input-tool grace, ⌘⌫ deletes immediately. Canvas deletion of an image tile only hides it.

## 14. Scene order and Phát liền
- Canvas is the only visible workspace. The centred "Phát liền" button opens a film player using a fixed snapshot in scene order: chosen ★ take, else newest completed, else a still. Its total excludes missing takes and unknown imported duration, marks inferred duration with ≈ and reports unknown counts.
- Reorder scenes from the inspector's scene-code control (▲/▼ or position entry) or Alt+↑/↓. Scene codes, film playback and ZIP order follow the new order; canvas positions stay put. Moves of one scene within a 1.5 s burst share one Undo and toast; moving back to the starting order removes that undo step.
- Stored old Table/Storyboard choices recover to Canvas. Storyboard code remains frozen and unbundled; no live Storyboard reorder interface is promised.
