# Spec v2 — user feedback round 1 (2026-10-01)

User feedback (Vietnamese, paraphrased):
1. "When I create a video, a video node should come out of that scene node (connected), so I can continue scenes from that video into other nodes."
2. "Prompt blocks and the auto references paragraph are redundant. The prompt itself contains the references, numbered like @image_1."
3. "Improve features and optimize so it runs on the web or as an app."

## 1. Take nodes (video output on the canvas)
- Every take (generation attempt) is a **Take node** on the canvas (`type: 'take'`, `id = take.id`), connected from its scene with an edge `out:<sceneId>-><takeId>` (always drawn in a subtle style when visible by edge mode; highlighted with the scene).
- Default placement: to the right of the scene, a horizontal strip: `x = scene.x + SCENE_W + 56 + i*(TAKE_W + 16)`, `y = scene.y`, i = take index within the scene (oldest first). Positions are stored on the take (`take.position`, runs store, not undoable) once the user drags it; until then computed.
- Take node (~220px wide): 16:9 thumbnail (poster; plays the webm on hover), `S03 · T2`, status (queued/processing with % bar/failed with reason/cancelled), duration·res, ★ toggle, menu (Xem, Chạy lại, Xoá). Source handle on the right (purple-ish `--video`).
- Collapsing: per scene "Thu gọn take" → only the starred (else latest completed) take node is shown, with a "+3" badge; project-wide toggle in the canvas toolbar "Take: Tất cả / Chỉ take chọn".
- Connecting a take to a scene = **video reference**: `scene.videoRefs: string[]` (take ids, ordered) → prompt tokens `@video_1, @video_2…` (Seedance 2.5 up to 10 reference videos, MiniMax-H3 up to 3). Edge id `vref:<takeId>-><sceneId>`.
- Drop a take's wire on empty canvas → ConnectMenu "Tạo cảnh tiếp nối từ video này": new scene placed below the source scene, `videoRefs=[take]`, `refs = source scene refs`, same settings, prompt prefilled `Continue from @video_1: ` (then the user types).
- Deleting a take (runs store) removes it from every scene's videoRefs and renumbers tokens (see §2).
- Only completed takes can be used as video refs (others: connection rejected with toast "Video chưa tạo xong").

## 2. Prompt = exactly what the user writes, with @image_N / @video_N
- REMOVE prompt blocks (data, store actions, sidebar panel, inspector toggles, import detection) and the auto "References…" paragraph and auto-continuity line. Remove scene `continueFrom` and the scene→scene "seq" edges/handles (continuity is now expressed by take → scene video refs).
- Numbering: images numbered 1..N in `scene.refs` order (each image of an asset gets its own number, primary first); videos numbered 1..M in `scene.videoRefs` order.
- The compiled prompt = the scene prompt text unchanged. Legacy `@Tag` mentions (asset tags) are still converted to `@image_N` at compile time for robustness, but the editor inserts `@image_N` directly.
- **Auto-renumbering**: whenever refs/videoRefs change (remove, reorder, insert, asset images added/removed/reordered), rewrite `@image_N`/`@video_N` tokens in the affected scene prompts so each token keeps pointing at the same image/video. Tokens whose image/video was removed become the asset name / "video S03-T2" plain text, and the user gets a toast with Undo. All in the same undo step as the ref change.
- Validation warnings: token number > available count ("@image_5 nhưng chỉ có 3 ảnh"), connected media never mentioned (info, still sent), over model limits, empty prompt, prompt length limit.
- PromptEditor: `@` popup lists (a) connected images with their numbers + thumbnails, (b) connected videos, (c) library assets not yet connected ("Nối & chèn" → connects and inserts the new number), filtered by typed text (matches name/tag/number). A token legend under the textarea: `@image_1 [thumb] Elara`, `@video_1 [thumb] S03·T2`; hovering a legend item highlights the token occurrences. Token highlighting inside the textarea via a backdrop mirror layer (colored `@image_N` teal, `@video_N` purple, invalid red).
- Scene card shows numbered avatars (badge 1,2,3 on each) and video ref thumbs with v1, v2.

## 3. Web + app, optimization
- PWA: `vite-plugin-pwa` (manifest: name "Bàn Dựng Phim", short_name "Bàn Dựng", theme/background `#0f1012`, icons 192/512 + maskable generated from an SVG logo), service worker precaching the app shell (autoUpdate), works offline. "Cài app" button in Settings (beforeinstallprompt) + hint text for Brave/Chrome/Edge.
- Persistence moved from localStorage to IndexedDB (idb-keyval stores `projects`, `runs`) with a one-time migration from the v1 localStorage keys; request `navigator.storage.persist()`. Debounced writes; flush on `visibilitychange: hidden` and `pagehide`.
- Code splitting: `React.lazy` for SceneTable, Storyboard and every dialog; manual chunk for `@xyflow/react` and `jszip`. Keep the initial JS small.
- Production: `npm run build` → `dist/` deployable to any static host; `start.bat` runs the built app via `vite preview` (fast) with a `dev.bat` for development.
- Performance: canvas must stay smooth with 60 scenes × 3 takes (≈240 nodes): memoized nodes, `onlyRenderVisibleElements`, posters as small JPEG thumbnails (generate a 320px thumb per take), video only loaded on hover/viewer.

## 4. Resizable side panels (done in the app shell)
- `components/common/PanelResizer.tsx`: drag the border between a side panel and the center to resize (left 200–520px, right 300–680px, center ≥ 360px), double-click resets, arrow keys ±16px (Shift ±64), dragging ~90px past the minimum collapses the panel. Widths persist in localStorage (`bdp:pref:leftW` / `bdp:pref:rightW`) and live in the CSS variables `--left-w` / `--right-w` on `.app`. Components must not hardcode panel widths.

## 5. Desktop app (.exe) — Electron + electron-builder
- `electron/main.cjs`: one BrowserWindow (min 1100×700, dark background `#0f1012`, title "Bàn Dựng Phim", no default menu bar; keep DevTools on Ctrl+Shift+I), loads the built app through a privileged custom protocol `app://bdp/` (standard + secure + supportFetchAPI + corsEnabled, registered before ready) that serves files from `dist/` — so IndexedDB/localStorage get a stable origin and data persists between launches. External links open in the default browser. Single-instance lock.
- Vite `base: './'` so the build works from the custom protocol and any static host. The service worker (PWA) is NOT registered inside Electron (`navigator.userAgent` contains "Electron" or `window.bdpDesktop`), only on http(s).
- `electron/preload.cjs` exposes `window.bdpDesktop = { version }` (contextIsolation on, nodeIntegration off).
- electron-builder (config in package.json "build"): appId `vn.bandungphim.app`, productName "Bàn Dựng Phim", files `dist/**` + `electron/**`, icon `build/icon.png` (512×512 fallback) with Windows `win.icon` = `build/icon.ico` (16–256 px) and NSIS `installerIcon` / `installerSidebar` / `uninstallerSidebar` / `installerHeader` bitmaps, all generated by `npm run icons` (`scripts/make-icons.mjs`) from the SVGs in `build/icon-source/` (the window icon on Windows is `dist/icons/icon.ico`), Windows targets **nsis** (assisted installer: choose directory, desktop + start-menu shortcuts, Vietnamese + English installer languages, artifactName `Ban-Dung-Phim-Setup-${version}.exe`) and **portable** (`Ban-Dung-Phim-Portable-${version}.exe`). Output dir `release/` (git-ignored).
- Scripts: `npm run desktop` (build + run Electron locally), `npm run dist:win` (build + both .exe). Since 0.5.0 every .exe is signed with the author's self-signed certificate (docs/SIGNING.md); README still explains the SmartScreen / "Unknown publisher" step for machines that do not trust it.

## 9. Demo credits vs real credits (2026-10-02)
User: "sửa lại khả năng hiển thị credit giữa demo và credit thật". Problem: the demo balance started at 377 (copied from the user's real canvasapp balance) and was shown as "377 credit · demo" — easy to mistake for real money.
- One source of truth: `useCreditInfo()` → `{ kind: 'demo' | 'canvasapp', balance, status: 'ok'|'loading'|'login-required'|'unavailable'|'error', refresh() }`. `kind` follows the active provider (`activeProviderId()`).
  - demo: `useRuns.credits` (local, fake). Default for NEW runs data: **1000** (existing saved balances are kept). Settings: "Đặt lại credit demo" (back to 1000) and "+100".
  - canvasapp: real balance from `/api/me` `credits_balance` through the desktop bridge, kept in a small store (`useRealCredits`), refreshed on login, after every submitted/finished canvasapp job, on window focus and at most every 60 s while visible; 401 → `login-required`. Never invent a number: show "—" until known.
- Visual language (both themes): demo = neutral/dashed "DEMO" pill with a flask icon and the tooltip "Credit giả lập — không phải tiền thật"; real = solid tinted pill "canvasapp · 1.234 credit" (+ "≈ 1.234.000đ" in tooltip), click = refresh; login-required = "canvasapp · Đăng nhập" action.
- Costs everywhere use one formatter: `formatCredits(n, kind, { short })` → "20 credit demo" / "20 credit" (short: "20 cr" + a small "demo" mark when demo). Scene card cost, run buttons, RunConfirmDialog (header shows the source; demo: balance before → after; canvasapp: current balance → estimated after, "trừ trên canvasapp khi job được nhận", never blocked by the demo balance), queue drawer footer, take viewer cost line ("đã trả bằng credit demo/credit canvasapp" via take.provider / take.charged), table totals, presets panel, multi-scene totals.

## 10. In-app top-up of canvasapp credits (2026-10-02)
User: "thêm khả năng nạp credit, thanh toán trong app" → chose: top up the user's OWN canvasapp account (not a SanoVids credit system).
Observed canvasapp flow (public client code, see docs/canvasapp-api-notes.md): `GET /api/auth/state` → `topup_enabled`; amount = integer VND, 10.000 ≤ amount ≤ 10.000.000, multiple of 1.000, credits = amount / 1.000, presets 30k/50k/100k; `POST /api/payments/topups { amount_vnd }` → `{ checkout_url, fields }` and the page auto-submits a hidden HTML form (POST) to `checkout_url` (SePay). SePay sends the browser back to canvasapp with `?payment=success|cancel|error&topup_order=<id>`; then poll `GET /api/payments/topups/{orderId}` → `status: pending|paid|reconciled|reconcile_required|expired|rejected` (order valid ~10 min; the site polls every 2 s for up to 2 min). History: `GET /api/credits/history?kind=all|topup|video|refund|adjustment&offset=0&limit=20` → `{ balance, items:[{type, description, status, delta, amount_vnd, created_at}], next_offset }`.
Design:
- Desktop only, through the canvasapp gateway session (`persist:canvasapp`). The bridge allowlist gains `POST /api/payments/topups`, `GET /api/payments/topups/:id`, `GET /api/credits/history`.
- New IPC `canvasapp:checkout({ checkoutUrl, fields })`: validates the URL (https only; host must end with `sepay.vn` — VERIFY on first real use, otherwise refuse with a clear message), opens a modal BrowserWindow in the canvasapp partition with a local page that POSTs the form, lets the user pay on the real SePay page (QR), and resolves `{ result: 'success'|'cancel'|'error'|'closed', orderId }` when the window navigates back to canvasapp.io.vn with `payment=…&topup_order=…` (or the user closes it). External links stay inside; no script injection into SePay.
- SanoVids never sees or types bank/card data; it never auto-confirms payments.
- UI: "Nạp credit" dialog (from the real-credit pill and the gateway settings section): presets 30k/50k/100k/200k + custom amount with validation and live "= N credit"; button "Mở thanh toán QR"; status view (Đang chờ thanh toán… with 10-minute countdown → Đã nhận tiền ✓ → refresh real credits; hết hạn / bị từ chối / đã huỷ / đang đối soát messages); "Lịch sử credit" tab with filters (Tất cả / Nạp / Tạo video / Hoàn / Điều chỉnh) and "Xem thêm". Disabled with explanations when not desktop, not logged in, or `topup_enabled` is false. Demo mode keeps the fake "+100 credit demo" only (clearly labelled, no payment).
- Tests: pure amount validation + status mapping + checkout URL validation; adapter/bridge with fakes. Never call the live API in tests.

## 11. Development mode replaces the demo (2026-10-02)
User: "đưa chế độ demo về thành chế độ phát triển dùng để tìm bug và sửa lỗi … có luôn các tính năng y như chế độ thật". The demo becomes a **development mode** that runs EVERY path of the real canvasapp mode, with no network at all.
- Providers: 'dev' (default, web and desktop) | 'canvasapp' (desktop only). 'mock' ("Demo cũ") only runs/shows/refunds takes saved before; a saved 'mock' choice becomes 'dev'. `activeProviderId()` = 'canvasapp' when chosen and the desktop bridge exists, else 'dev'.
- 'dev' = the REAL canvasapp adapter / api / desktop transport (`createCanvasappProvider({ id: 'dev', … })`, own namespaced storage `bdp:dev:client/…`, polling every 3 s via `minPollIntervalMs`) over `devBridge()` (simulated electron gateway: same allowlist as main.cjs, 2 MB / 20 MB caps, job-list cache, login / checkout "windows" as in-app sheets) and `devServer()` (simulated canvasapp: auth, /api/me, video profiles, projects + strict canvas, uploads, strict jobs with idempotency and real prices, wall-clock progression 'fast' ≈ 8 s / 'realistic' 60–90 s, stream rendered from the uploaded pictures labelled @image_N, top-up orders + SePay outcomes, credit history). State persists (localStorage `bdp:dev:state` / `bdp:dev:config`, blobs in IndexedDB `sanovids-dev`); first run: logged out, 1000 credit dev, top-up on. ONE account for every tab, like the real site: each tab's copy of the server re-reads the saved account before every request / change and on the window `storage` event (`sync()`). Jobs and top-up orders move on by the clock for every endpoint (/api/me sees a refund or a payment that is due). The saved account stays under 1.5 M characters (oldest finished jobs go first; trimmed jobs / uploads take their IndexedDB blobs with them); a save that still fails shows in the panel (`persistProblem`). A damaged saved record is dropped, never fatal (the panel also offers the wipe when it cannot read the server).
- Faults for finding bugs: per endpoint, one-shot or sticky — network, lost-response, processed-then {status, json}, response {status, json}, slow; job-level: next job fails / expires, next N downloads fail, session expires (counted as an armed fault until the next login). Faults combine: every matching "slow" adds its delay, and ONE other rule decides the outcome — a rule for the endpoint before a "*" rule. "Invalid canvas payload (400)" fires twice (the adapter retries the canvas once with only the current scene). Request log (300 entries) of what the app sent and got.
- Words: the dev API client and the dev provider are wrapped (`providers/dev/wording.ts`): their messages say "canvasapp giả lập" and "kiểm tra trong Bảng phát triển", never send the user to canvasapp.io.vn for a simulated job; the engine's "không rõ đã gửi" / "không tải được video" texts have dev versions (`unknownSubmitError(pid)`, `downloadFailedError(detail, pid)`). Polling: the engine reads the simulated job list every 3 s; the adapter / gateway caches last 2 s (stamped when the answer arrives, so no poll is served stale).
- Top-up across a provider change: an order in flight stays on the gateway it was created on; once it is over, an order of the other gateway is announced and let go (the sheet, its balance, login and history follow the active gateway — development mode never calls the real site because of an old order).
- Credits: kind 'dev' ("credit dev", DEV_CREDIT_HINT) read from the simulated /api/me through `activeGateway()`; the balance store resets when the active gateway changes.
- Tests: providers/__tests__/dev-server.test.ts (server, bridge vs main.cjs allowlist, faults, top-up, persistence) and dev-e2e.test.ts (real engine + adapter + app wiring); the canvasapp e2e fake imports the same validators (providers/dev/validate.ts).
- UI — "Chế độ Phát triển" everywhere the old demo was (`components/dev/`, `dv-` classes; pure texts / rules in `components/dev/devModel.ts`, tested):
  - Credit pill (`creditPillModel` tone 'dev', `sim`): dashed neutral "DEV 1.000 credit" from the simulated /api/me, "DEV Đăng nhập" (→ simulated login sheet), "+" = top-up (simulated SePay). Cost labels everywhere: "20 cr" + a small "dev" mark (`CREDIT_MARK`), class `is-sim`, tooltip DEV_CREDIT_HINT. Run dialog / queue / take viewer / toasts name "credit dev", "máy chủ giả lập", "Bảng phát triển". "Demo" now only names legacy mock takes ("Demo cũ"); the sample project is "Dự án mẫu".
  - Sheets above every dialog (App root, `DevSheets`, lazy): "Đăng nhập canvasapp (giả lập)" (Đăng nhập / Đóng) and "Thanh toán SePay (giả lập)" (amount, order, placeholder QR, outcome after success, delay, "paid on the phone then closed"; Thanh toán thành công / Huỷ / Lỗi thanh toán / Đóng cửa sổ). Keyboard: focus in/out, Tab trapped, Escape = close; `data-top-overlay` keeps the Modal / lightbox / player below from reacting.
  - "Bảng phát triển" (dialog kind 'dev', `actions.openDevPanel(tab)`; top bar bug button with the number of armed faults — dev only —, Settings › Nhà cung cấp video / Chế độ Phát triển, queue drawer, run dialog, take viewer): Trạng thái (server-side login / logout / session end, balance set / ±100 / 0 / 1.000, speed, topup_enabled, dedupe, exposeKey, 402/400, latency, failRate, model profiles — can_create, disabled_modes and durations / resolutions / ratios left out of the lists per model (Seedance's narrowed lists apply, MiniMax-H3's are ignored like canvasapp's page does) — with what SanoVids knows of them (`devModel.limitsStatusText`: not read / read at HH:MM:SS / older than 10 min / unreadable → fallbacks; a warning when it differs from the toggles, `limitsDifferFromConfig`) and "Đọc lại ngay" (a `changed` read — at once, never the inspector's 5 s click limit: the panel never re-reads by itself, so the real site's 10-minute cache stays reproducible; "Đăng nhập ngay" and every login re-read the same way), wipe = `resetDevMode()`), Gây lỗi (one-click faults, one-shot or "giữ", job faults, session end, custom rule builder, armed list), Nhật ký (filter, problems only, expandable JSON, "Copy nhật ký" JSON with the server state; "Kiểm tra nhân vật" for every POST /api/video-jobs: upload_ids in order = @image_N → SanoVids picture (upload filename → image id) → asset, @image_N without a picture flagged), Job & đơn nạp (force complete / fail / expire, which take a job belongs to, which bridge node it ran on — "node S03" = that scene of the open project, "node cũ S03" = the node older builds named by the scene id alone, "node khác" = another project or a deleted scene (`devModel.jobNodeOwners` / `jobNodeText`) —, settle orders, uploaded pictures).
  - Settings: "Nhà cung cấp video" section (Phát triển | canvasapp.io.vn; the account row of the ACTIVE gateway, tagged DEV in development mode, + "Bảng phát triển"); the old mock / demo-credit sections are replaced by "Chế độ Phát triển" (summary, speed, shortcuts to the panel).
